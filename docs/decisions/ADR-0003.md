# ADR-0003: 阈值门禁策略 (floor 硬下限 + 实测基线回填, 两环境两列数字)

- 状态: Accepted (2026-10-08)
- 决策者: 主理人 晨星；架构师 楼构新
- 相关文档: `docs/ARCHITECTURE.md` 第 9 节, ADR-0002
- 影响范围: `eval/baseline.py`, `eval/scorecard.py`, `src/worldforge/eval/baseline.json`, `scripts/record_baseline.py`, `.github/workflows/ci.yml`

---

## 背景

| 问题 | 说明 |
| --- | --- |
| 门禁形同虚设 | 门限若写成 `0.0` 或「暂不校验」, 任何退化都能通过, 等于没有门禁 |
| 不能凭空编数字 | 未实测就写死基线值, 要么高得永远挂 (阻塞开发), 要么低得永远过 (掩盖退化) |
| 两套栈的质量差一个量级 | 零依赖默认栈 (散列嵌入 + 抽取式 mock LLM) 与生产 extras 栈 (真嵌入 + 真 LLM) 分数不可比, 一套门限必然错杀或漏过 |
| 抖动与回归要分开 | 数值抖动不该挂 CI, 真回归必须挂 CI |

主理人裁决: 允许「流程 + floor 下限」先落地, 实现阶段跑 `scripts/record_baseline.py` 生成实测基线后回填; **floor 必须是会失败的硬值**, 不能写 `0.0`; 回填后把实测值贴着基线设 (基线 * 0.95)。

---

## 决策

### D1 双层门限: floor + baseline

```
threshold = max(floor, baseline * 0.95)
```

| 层 | 来源 | 性质 | 何时生效 |
| --- | --- | --- | --- |
| `floor` | 人工设定的绝对下限, 入库写死 | 硬, 必须能失败 | 立刻生效, 不需要等基线 |
| `baseline` | `scripts/record_baseline.py --runs 5` 实测均值 | 硬, 贴着实测 | 回填后生效 |

**未回填时 `threshold = floor`, 门禁立即生效**, 不存在空窗期。`baseline.json` 中的 baseline 列一律初值为 `null`, 由回填步骤写入。

### D2 floor 必须是会失败的硬值

主理人指定: `doc_hit_rate` floor = `0.60`, `MRR` floor = `0.50`。其余指标按下表同量级设定, 全部为「正常系统必过、退化系统必挂」的值, 禁止写 `0.0` 或 `-1` 作为硬门限。

### D3 两环境两列数字

| 环境 | 代号 | 构成 | 用途 |
| --- | --- | --- | --- |
| 环境 A | `zero-dep` | 零依赖默认栈: HashingEmbedder + InMemoryExactIndex + BM25 + LexicalReranker + ExtractiveMockLLM + RuleBasedPlanner | `scripts/verify.py` 与 CI 的 default job |
| 环境 B | `prod-extras` | 生产 extras 栈: fastembed + FAISS(CPU) + 真 LLM (llama-cpp / Ollama) | CI 的 extras job, 需 GPU/大内存的 job 标为可选 |

两个环境各有一套完整的 floor 与 baseline, 互不比较, 分别判定。

### D4 门限表

| 指标 | 环境 A floor | 环境 A baseline (待回填) | 环境 B floor | 环境 B baseline (待回填) | 类型 | 判定 |
| --- | --- | --- | --- | --- | --- | --- |
| `doc_hit_rate@5` | 0.60 | null | 0.60 | null | 硬 | `>= max(floor, baseline*0.95)` |
| `recall@10` | 0.55 | null | 0.65 | null | 硬 | 同上 |
| `mrr` | 0.50 | null | 0.50 | null | 硬 | 同上 |
| `grounding` | 0.55 | null | 0.65 | null | 硬 | 同上 |
| `faithfulness` | 0.50 | null | 0.60 | null | 硬 | 同上 |
| `tool_route_accuracy` | 0.70 | null | 0.85 | null | 硬 | 同上 |
| `tool_call_success` | 0.90 | null | 0.90 | null | 硬 | 同上 |
| `ndcg@10` | 无 floor | null | 无 floor | null | 软 | 只告警, 相对下降 > 2% 时 warn |
| `rank_corr` | 无 floor | null | 无 floor | null | 软 | 只告警; 常量输入恒 0.0, 不参与均值 |
| `latency_p50_ms` | 无 floor | null | 无 floor | null | 软 | 不挂 CI, 阈值 `-1` |
| `latency_p95_ms` | 无 floor | null | 无 floor | null | 软 | 不挂 CI, 阈值 `-1` |

说明: 软指标 (ndcg / rank_corr / 延迟) 不设 floor 是**有意设计** -- 它们要么数学上可能恒为 0 (常量输入), 要么本质是抖动量 (延迟), 设硬门限只会制造误报。硬指标的 floor 一律是能失败的值。

### D5 回填流程

| 步 | 命令 | 产物 |
| --- | --- | --- |
| 1 | `python scripts/record_baseline.py --env zero-dep --runs 5` | 环境 A 的 `mu` 与 `sigma` |
| 2 | `python scripts/record_baseline.py --env prod-extras --runs 5` | 环境 B 的 `mu` 与 `sigma` |
| 3 | 写入 `src/worldforge/eval/baseline.json` | `baseline` 列由 `null` 变为实测值 |
| 4 | `python -m pytest tests/test_eval_gates.py` | 验证 `threshold = max(floor, mu*0.95)` 计算正确 |
| 5 | 提 PR, 说明基线来源与运行环境 | 基线入库, 之后由 CI 守护 |

回填后示例 (假定环境 A 实测 `doc_hit_rate@5 = 0.84`): `threshold = max(0.60, 0.84 * 0.95) = max(0.60, 0.798) = 0.798`。真回归掉到 0.70 必挂; 抖动 0.83 不挂。

### D6 基线变更纪律

| 规则 | 说明 |
| --- | --- |
| 基线入库 | `baseline.json` 随代码提交, 不接受运行时动态生成 |
| 有意变更 | 行为变更导致基线必须调整时, 同 PR 修改 `baseline.json` 并在描述里写明原因 |
| 单向上调 | 人工只允许上调 baseline, 下调必须附 root cause 分析 |
| 环境隔离 | 环境 A 与 B 的基线分文件段存储, 禁止互相覆盖 |

### D7 门禁行为

| 场景 | HTTP `POST /v1/evaluate` | CLI / CI |
| --- | --- | --- |
| 全部硬指标过 | 200, `passed=true` | 退出码 0 |
| 有硬指标未过 | 200, `passed=false` (接口本身成功) | 抛 `EvalGateError`, 退出码非 0 |
| 软指标下降 > 2% | 200, `warnings` 非空 | warn, 退出码 0 |

---

## 理由

| 维度 | 说明 |
| --- | --- |
| 能力匹配度 | `max(floor, baseline*0.95)` 同时满足「立刻生效」与「贴着实测」两个要求 |
| 成本 | 零成本; 回填需跑 5 轮评估, 一次性开销 |
| 延迟 | 延迟指标明确排除在门限外, 避免 CI 因机器负载偶发失败 |
| 运维复杂度 | 中: 需维护两套基线; 由 D6 的纪律约束 |
| 风险 | 主要风险是「环境 B 在无 GPU runner 上跑不动」 -> 已把 extras job 标为可选, 环境 A 门禁始终有效 |

为什么是 `0.95` 而不是 `mu - 3*sigma`: 主理人明确要求「贴着基线设 (基线 * 0.95)」。相对比例门限在指标量纲不同时行为一致, 且不依赖 sigma 估计 (5 轮样本的 sigma 估计本身不可靠)。若后续发现某指标抖动幅度超过 5%, 在 `baseline.json` 里为该指标单独覆盖系数。

## 后果

### 正面

| 项 | 说明 |
| --- | --- |
| 无空窗期 | floor 立即生效, 基线未回填时门禁已在守护 |
| 真回归必挂 | 贴基线 5% 的门限对真实退化敏感 |
| 抖动不挂 | 5% 缓冲 + 延迟指标不入门限 |
| 两套栈各自可比 | 环境 A / B 分开判定, 不会用生产分数错杀默认栈 |
| 可审计 | 基线入库 + 变更需 PR 说明 |

### 负面

| 项 | 说明 | 缓解 |
| --- | --- | --- |
| 初期可能误报 | floor 是拍的, 若默认栈实际质量低于 floor, 一上来就红 | floor 已按「正常系统必过」量级设定; 若实测确实低于 floor, 说明实现有 bug, 红是对的 |
| 两套基线维护成本 | 环境 B 需要 extras 运行环境 | extras job 标为可选; 环境 B 基线可延后回填 |
| 5% 缓冲对高基线指标偏松 | 基线 0.95 时门限 0.9025, 掉了 0.05 才挂 | 可接受: floor 保底, 且软告警在 2% 就提示 |
| 软指标无强制力 | ndcg / 延迟退化不会阻断 | 进 PR 模板对比表, 由 reviewer 把关 |

## 替代方案

| 方案 | 内容 | 为何否决 |
| --- | --- | --- |
| A. 门限全写 `0.0` 或 `-1`, 等实测再填 | 最省事 | 主理人明确否决: 门禁形同虚设, 期间所有退化都能合入 |
| B. 只写死一套拍脑袋的绝对值 | 例如统一 0.8 | 与两套栈的质量差冲突: 默认栈达不到, 生产栈太松 |
| C. 只用 `mu - 3*sigma` | 统计学门限 | 5 轮样本的 sigma 不可靠; 与主理人「基线 * 0.95」的裁决不一致; sigma 为 0 时退化成 `mu`, 零容忍 |
| D. 相对门限 + 无 floor | 只比基线 | 基线本身偏低 (例如 0.3) 时, `0.285` 也能通过, 失去绝对质量把关 |
| E. 延迟也进硬门限 | p95 > 500ms 挂 CI | CI runner 负载波动大, 必然偶发失败, 违反「抖动不挂」原则 |
