# ADR-0002: 确定性优先

- 状态: Accepted (2026-10-08)
- 决策者: 主理人 晨星；架构师 楼构新
- 相关文档: `docs/ARCHITECTURE.md` 第 9/10 节, `docs/ARCHITECTURE.md` 失败模式 FM-08/FM-09/FM-14/FM-17/FM-18
- 影响范围: `core/seeding.py`, `core/sortutil.py`, `config.py`, `pipeline.py`, `eval/`, `observability/`

---

## 背景

已实测出现的非确定性问题:

| 现象 | 根因 |
| --- | --- |
| 评估第二次跑分数变了 | 复用同一 Pipeline, 索引与缓存残留 |
| 评估指标系统性偏低 | 适配器读对象上的 `last_*` 缓存字段, 拿到上一轮结果 |
| 常量输入的秩相关被算成 `+1.0` | 标准差为 0 时相关未定义, `0/0` 被兜底成 1.0, 掩盖真实退化 |
| 同分数结果顺序两次运行不一致 | 只按 `score` 排序, 同分顺序随底层字典序漂移 |
| 开 numpy 与不开结果有微小差异 | 两套实现浮点累加顺序不同 |
| 延迟污染断言 | 墙钟字段混进业务对象, 导致双跑比对必失败 |

如果确定性不优先, 评估门禁就失去意义: 门限再严也分不清「真回归」与「随机抖动」。

---

## 决策

### D1 默认 DocStore 为 `MemoryDocStore`

`WORLDFORGE_DOCSTORE=memory` 为默认值。`sqlite` (stdlib `sqlite3`) 保留为零依赖可选项, **必须显式设置 `WORLDFORGE_DOCSTORE=sqlite` 才启用**, 不作为默认。

主理人裁决理由与架构侧一致: 评估必须在全新管道上跑以保证确定性, 持久化存储会引入跨 case 的残留状态。

### D2 评估与关键单测使用全新管道

| 场景 | 要求 |
| --- | --- |
| `eval/runner.py` 每个 case | 调用 `build_pipeline(env)` 新建, 禁止复用 |
| 跨 case 复用 | 禁止; 阶段之间如需清洗走 `clear()` |
| 模块级单例 Pipeline | 禁止; `pipeline.py` 不保存全局 `_PIPELINE` |

### D3 `deterministic_view()` 排除墙钟延迟

排除键集合 (`core/seeding.py`):

```
ts, timestamp, started_at, ended_at, created, created_at,
latency_ms, duration_ms, wall_ms, elapsed_ms,
pid, hostname, thread_id, uptime_s
```

同时: float 统一 `round(x, 6)`; `-0.0` 归一为 `0.0`; dict 按键排序; set 排序后转 list。

### D4 固定种子与零采样

| 项 | 值 |
| --- | --- |
| `WORLDFORGE_SEED` | `1337` |
| `random.seed` / `PYTHONHASHSEED` | 由 `seed_everything(seed)` 统一设置 |
| LLM `temperature` | 恒为 `0.0`, 评估与默认路径禁止采样 |
| 数据集顺序 | 固定, 不打乱, 不并行 |

### D5 统一稳定排序

所有排序主键一律 `(-score, id)`, 经 `core/sortutil.py:stable_sort()`。禁止只按分数排序。

### D6 延迟单独统计, 不进确定性断言

| 规则 | 说明 |
| --- | --- |
| 业务对象禁含时间字段 | `Hit` / `Completion` / `ToolResult` / `Plan` / `Evidence` 一律不含墙钟 |
| 延迟只从 `Observer` 的 span 出 | 唯一允许的墙钟产生点 |
| 延迟进 `perf` 通道 | 评估返回体单独的 `perf` 键; HTTP 侧走 `/v1/metrics` 的 histogram |
| 断言排除 | `assert_deterministic` 与 `deterministic_view` 自动剔除墙钟键 |
| P95 只告警 | 门限 `-1`, 不挂 CI |

### D7 禁止 `last_*` 缓存字段, 评估显式捕获本次返回值

类型定义中不出现 `last_answer` / `last_hits` / `last_result` 之类的字段。评估器必须接收本次调用显式返回的 `dict`, 不得从对象上读缓存。`tests/test_eval_runner.py` 守护。

### D8 常量输入的秩相关返回 `0.0`

`core/rank_corr.py`: 任一方标准差为 0 时直接返回 `0.0`, 不做 `0/0` 兜底, 且不参与门限均值计算。

### D9 numpy 加速必须过 parity 测试

`core/accel.py` 的 numpy 路径与纯 Python 路径逐元素对齐, `atol=1e-9`。numpy 缺失时该测试 skip, 不得 fail。

## 理由

| 维度 | 说明 |
| --- | --- |
| 能力匹配度 | 确定性是「评估门禁能区分真回归与抖动」的前提, 没有它 ADR-0003 的门限等于掷骰子 |
| 成本 | 零额外成本, 只是纪律约束 |
| 延迟 | 无影响; 延迟仍被采集, 只是不参与相等性断言 |
| 运维复杂度 | 略增: 每个 case 新建管道比复用慢, 需要接受评估耗时 |
| 风险 | 主要风险是「为了确定性牺牲了真实性」-- 通过两环境两列数字 (ADR-0003) 对冲, 生产环境另有基线 |

关键取舍: 宁可评估慢一点, 也不要出现「同样代码今天过、明天挂」。

---

## 后果

### 正面

| 项 | 说明 |
| --- | --- |
| 门限可信 | 挂了就是真回归, 不挂就是没退化 |
| 双跑可校验 | `assert_deterministic(fn, runs=2)` 能直接验证任意组件的确定性 |
| 可复现 | 外部贡献者 clone 后跑出的分数与 CI 一致 |
| 坑可守护 | 12 个实测坑中至少 5 个 (FM-08/09/14/17/18) 直接由本 ADR 的纪律覆盖 |

### 负面

| 项 | 说明 | 缓解 |
| --- | --- | --- |
| 评估变慢 | 每个 case 重建管道 + 重新摄入 | 黄金集控制在百级 case; 延迟敏感的规模测试另走 `scripts/bench.py`, 不进门限 |
| 无法测试真实持久态 | Memory DocStore 掩盖了 sqlite 路径的状态残留问题 | sqlite 路径另有一组专属测试, 但**不参与**分数门限 |
| 丢失抖动信号 | 延迟指标不挂 CI, 性能退化只能靠人看 | `scripts/bench.py` 输出进 PR 模板的对比表 |
| 采样能力被禁 | `temperature=0` 意味着默认路径不展示多样性生成 | 生产路径不受限, 只是不进确定性断言 |

## 替代方案

| 方案 | 内容 | 为何否决 |
| --- | --- | --- |
| A. 默认 sqlite 持久化 | DocStore 默认 `sqlite`, 保证重启可恢复 | 违背「评估在全新管道上跑」的裁决; 跨 case 残留是 FM-18 的直接诱因; 降级为非默认开关已足够 |
| B. 评估复用单例管道 + 每轮 `clear()` | 省去重建开销 | `clear()` 覆盖不到所有内部状态 (工具调用计数、observer 缓冲、嵌入缓存), 实测已证明会漂移; 收益不抵风险 |
| C. 允许墙钟字段进断言, 用容差比较 | `abs(a.latency - b.latency) < 50ms` | 容差是猜的: 慢机器上必然偶发失败, 快机器上又掩盖真回归 |
| D. 常量秩相关返回 `1.0` 并标注 | 保持现状 + 文档说明 | 会把「重排器完全失效、输出恒定分数」误判为满分, 门限形同虚设 |
| E. 门限只比大小不看方差 | 简单阈值 | 与 ADR-0003 冲突: 无法区分抖动与回归, 必然频繁误报 |
